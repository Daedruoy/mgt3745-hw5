# DDR-001: F-07 status-tracking feature (bolt.new)

## Task

Implement F-07 from FEATURES.md: a chair marks their own update as completed, and the completed status is visible to brothers without the secretary or president needing to follow up individually. Specifically, the four EARS rows in FEATURES.md's Acceptance section covering: (1) a chair marks their own update completed and the change persists, (2) status displays alongside each update's other details, (3) a chair who did not submit an update is rejected if they attempt to change its status, (4) the status update is persisted via a new Worker endpoint using bind(). Scope was limited to index.html, styles.css, and app.js.

## Tool and model

bolt.new (StackBlitz), free tier, accessed 2026-09-29. The build ran in bolt's "Standard" mode. bolt.new does not disclose the specific underlying model to free-tier users anywhere in its interface; I checked the mode selector, project settings, and the generation log, and found no model name or version exposed. This is itself worth noting as a Trust Boundary gap: I cannot verify which model generated code that now runs against my production infrastructure, only that it came from bolt.new's Standard tier on this date.

## Economic rationale

Estimated build-by-hand time for a feature this size, based on HW3/HW4 pace: roughly 1 to 1.5 hours (a new Worker endpoint, ownership check, two new UI elements, CSS). Actual time spent: bolt's generation took under a minute; my review, identifying the fake-entry hack, checking production for contamination, writing the real endpoint, rewriting four client-side functions, and fixing a contrast failure, took approximately 2 hours. Net: review time exceeded the honest build-by-hand estimate. This delegation was not a net time savings. It was still worthwhile, since the review process surfaced a real architectural mistake (the fake-entry workaround) and a real security gap (no ownership check at all in bolt's version) that I would likely not have caught as clearly building alone under time pressure, but the economic case for delegating this particular feature is negative, and this DDR says so directly rather than rounding up.

## Trust Boundary

What crossed: all context files (PROJECT.md, FEATURES.md marked to scope to F-07 only, STYLE.md, STANDARDS.md, TOOLS.md) and the current index.html, styles.css, and app.js were pasted into bolt.new as prompt text. My deployed Worker URL was included so bolt's generated code could call it. To whom: bolt.new and StackBlitz, and the model vendor behind bolt's generation. Since: 2026-09-29. Accountable: me. No GitHub connection was made; the project was downloaded as a zip only, per the Trust Boundary decision made in class.

Reverse crossing: bolt's output brought back a full Vite/React/TypeScript/Tailwind project scaffold I never asked for, alongside the three files I did ask it to touch. More significantly, bolt made unauthorized write requests against my live, deployed Worker during generation, not a sandboxed environment. I found three test entries in production (ids 6, 7, 8: chair_name values "Test Status" and "x", timestamps minutes apart on 2026-09-29) that I did not create. I confirmed this via curl against /entries and removed them with wrangler d1 execute --remote --command "DELETE FROM entries WHERE id IN (6, 7, 8)". This is a real, unauthorized crossing: I told bolt to "call the existing Worker," not to write test data into it, and it did so without asking.

## Verification performed

The seven-question Session B checklist (docs/CHECKLIST.md), applied by hand to bolt's raw output before any integration. Each of the four F-07 EARS rows was checked individually against the generated code. STYLE.md's token values were compared against the CSS bolt generated. package.json was read to check for added dependencies.

## Findings

**Checklist results on bolt's raw output:**
- Scope: partly pass. The three named files were edited, but the delivered zip also contained an unrequested Vite/React/TS scaffold.
- innerHTML or SQL concatenation: pass. All rendering used textContent; no client-side SQL.
- STYLE.md token fidelity: fail. Bolt introduced its own colors not in STYLE.md (e.g., a green success color).
- Dependencies: fail at the zip level. package.json listed Supabase, React, lucide-react, and Tailwind. None were imported by the actual app.js logic, but Supabase's presence directly contradicts ADR-002's decision to use Cloudflare D1, and an unused dependency in a delivered artifact is still a finding.
- Calls the Worker vs. invents storage: pass on paper, wrong in design. Bolt did call POST /entries rather than using localStorage, but it used this as a workaround: it stored status changes as fake regular entries (initiative: "_status", chairName: "system", with a JSON payload hidden in update_title carrying the target entry id and new status), then filtered these out and reconstructed status client-side on every page load.
- EARS pass count on bolt's raw output: 1 pass, 1 partial, 2 fail (see below).
- Unverifiable: the fake-entry hack's long-term behavior was unverifiable without running it, since it relied on a client-side JSON.parse inside a silent catch block that would fail invisibly on any malformed marker.

**EARS row results, bolt's raw output:**
- Row 1 (status persists): partial. It persisted, but nothing tied the change to the submitting chair, since there was no ownership check at all.
- Row 2 (status displays): pass, with one wording mismatch. The badge read "Active" instead of "Pending," diverging from the spec's own language.
- Row 3 (reject a non-owner): fail. The "Mark completed" button rendered on every update regardless of who was viewing it. Bolt's own generated comment in app.js acknowledged this gap rather than hiding it.
- Row 4 (new endpoint using bind()): fail. Bolt did not, and could not, touch worker.js, since the prompt explicitly restricted it to the three page files. It worked around the missing endpoint instead of surfacing that the constraint conflicted with the requirement.

**The specification conflict.** My own prompt instruction said "call the existing Worker" and separately restricted bolt to editing only index.html, styles.css, and app.js. But EARS Row 4 required a new endpoint, which necessarily means editing worker.js. These two instructions were in direct tension, and bolt resolved the tension by inventing the fake-entry workaround rather than asking or flagging the conflict. This is a specification-writing lesson as much as a tool-limitation finding: the prompt should have either scoped worker.js in explicitly for this one endpoint, or the F-07 feature should have been descoped to not require a new endpoint at all.

**What I changed.** I discarded bolt's fake-entry hack entirely. I wrote a real PATCH /entries/:id/status endpoint by hand in worker.js, using bind() for both the id and the new status value, with a soft ownership check (comparing a submitted chairName against the stored chair_name, returning 403 on mismatch). I added a status column to the D1 schema via ALTER TABLE. I rewrote four client-side functions (postStatusUpdate, buildStatusBadge, buildMarkCompleteButton, handleMarkComplete) to call the real endpoint, corrected the "Active" label to "Pending," and deleted applyStatusMarkers entirely, since status now returns directly on each entry from GET /entries. I tested the new endpoint directly with curl: a valid status change returned 200 with the updated entry; a mismatched chair name returned 403 with the correct message; an invalid status value returned 400 naming the problem. All three passed. I then tested the full integrated flow live in the browser: posting an entry, marking it complete via the name-confirmation prompt, and confirming the badge updated correctly.

**What I still cannot fully verify.** The ownership check is a soft check, a string comparison against a name the client supplies, not real authentication. Anyone who knows or guesses a chair's submitted name can mark that chair's update complete. This is a known, documented limitation, not an oversight; real authentication was out of scope for this assignment and this project's current stage. I also used a native window.prompt() for name confirmation rather than an inline form field, a deliberate but crude UX shortcut under time constraints, not a hidden one.
